**2026-06-10 (dev-side analysis)** — **Sidescan artifact root-caused** from
`~/data/logs/bizzy_sidescan/bag_2026-06-09T12.30.06_sidescan_raw` (60 s live
transmit; GCV-20, all 3 channels ~10.6 Hz, clean cadence, 0% saturation, no
dropouts — acquisition is healthy). The "solid constant bright lines" are
**packet metadata mis-decoded as sonar samples** in the `garmin_sidescan`
driver:

- A scan line = 7 UDP packets accumulated by `PingAssembler`
  (`garmin_sidescan/decode.py`). `echo_layer()` (GCV-20) / `dark_layer()`
  (GCV-10) slice each packet's samples as `[FH+4 : SH/SHS or end-of-packet]`,
  but each packet's layer is actually `[leading per-ping sub-header (first
  packet only)] + [real samples] + [~12–16 B trailer]`. Neither the leading
  sub-header nor the trailer is stripped.
- **Trailer** (`43 8X 96 03 | 49/4a XX YY | 52 80 10 | 5a …`, with `XX` an
  incrementing chunk counter) lands at each of the 7 packet-concatenation
  boundaries → the evenly-spaced bright vertical stripes. Verified the exact
  bytes match the constant columns (down ch: idx 302=`0x0049`, 303=`0x8052`,
  304=`0x5a10` = `49 00 52 80 10`).
- **Leading sub-header** (a constant `XXYY` pair repeated ~19 samples; down
  `b2 ad…`, side `32 b3…`, varies per ping) → the bright near-range band.
- Affects **all three channels** (down-look 0x0d has no `SH` terminator so
  reads to packet end; side-scan 0x0e/0x0f finds `SH` but the trailer sits
  *before* it, so it's still included).
- Also unpopulated (separate, lower-priority): `sample_rate`=0 (only derived
  when a range was commanded), `ping_info.frequency`=0 (not in payload; needs
  `freq_*_hz` params), `sample0`=0.

Fix lands in `marine_tools/garmin_sidescan/decode.py` (strip per-packet
trailer + first-packet leading sub-header). Reference decoder + packet notes
exist at `~/garmin_sidescan` (`gcv_decode2.py`, `GCV20_LIVE_NOTES.md`).
Analysis scripts: `.agent/scratchpad/ss_*.py` (workspace repo). Needs a
`marine_tools` issue + worktree to fix. The mid-run range-scale changes
(variable samples/ping) are a separate, lower-priority display concern.

## Lessons Learned

- **One spurious segmentation point should not trip a hard stop.** The reflex
  CA path has no points-persistence/confidence floor; the only runtime lever
  is stop-box geometry, which trades away real-obstacle reaction distance. The
  durable fix is a min-points/persistence filter — follow-up issue.
- **Core can wedge mid-run with discovery still healthy.** Diagnostic tells:
  discovery-OK-but-no-subscription-data points at core (not the link); a
  frozen embedded timestamp on a relayed topic means the relay is stuck, not
  the link. Restarting core is the only known recovery — core needs a
  liveness/health signal and `command_bridge_sender` a stale-frame watchdog.
- **Re-point sonar_logger off the decommissioned DeltaT.** New sonars (M3)
  silently go unrecorded until the logger YAML is updated and the logger is
  rebuilt + relaunched; `install(DIRECTORY)`-copied config won't hot-reload.
- **Track the deployment phase.** During recovery the boat-side agent
  over-investigated the intended stack-down (silent marine channel, empty node
  graph, no router) as a fault instead of asking — phase had moved to recovery.
