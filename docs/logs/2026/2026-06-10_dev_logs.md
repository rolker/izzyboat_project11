## Lessons Learned

- **Bridgeable control needs explicit both-direction wiring and a real
  protocol.** marine_tools#31 ("controls in rqt") merged but never worked on the
  water: `state`/`change_state` were never added to the udp_bridge *sender*
  config, and the rqt plugin only refreshes its topic list on a manual button.
  QoS was a red herring. The durable answer is a generic bridgeable
  device-control protocol (ADR-0002 / unh_marine_autonomy#140), with the
  bizzyboat bridge config wired both directions.
- **The CUBE grid outgrows the bridge on long surveys.** A monolithic
  `GridMap`-over-bridge fails past a size threshold; the durable fix is bounded
  tile-sync (unh_marine_autonomy#86). `clear_grid` is the manual stopgap. Also:
  a very large message publishing slowly reads as *silence* in a short
  `topic hz` window — don't mistake it for a dead publisher, and don't chase
  code/TF when the operator has ground truth.
- **Line-tracking is gated by reference stability, not speed.** The boat tracks
  lines cleanly at 3 kn with a stable reference; mid-line re-sends/`override
  goto`/`replace_task` trigger replan bursts that saturate the cross-track PID
  (marine_nav#66). Operationally: pre-plan long straight lines and avoid mid-line
  re-sends.
- **GCV range is chartplotter-mediated.** The driver can't pin range without an
  auto-range-disable command; at minimum it should report the *true* active range
  from the `:51000` CDP config stream (marine_tools#32).
