## Summary

BizzyBoat transited ~12.3 km from the Judd Gregg pier to Appledore, Isles of
Shoals, and worked on station. Activation 06:59 (pandy) / 07:04 (gabby); boat
tied up 16:27; field side closed out 17:45. **The survey produced a lot of good
data** (operator). The transit itself was uneventful and precise — it tracked its
computed ETA to within a few minutes across two and a half hours while holding
cross-track under 0.2 m.

The day's real work was diagnostic, and it landed three root causes. The operator
link degraded repeatedly, and it was traced on the water to the **admission
controller**, not to bandwidth or to Starlink: a brief loss event slams the cap
to 0.8 × reported goodput and recovery is additive-only, producing a ~37 s outage
from a momentary trigger. The **trackline failed** with `survey_line_failed`
because `bizzy/map_tide` was absent from the TF tree — and the cause was not the
tide or the datum but the **flat-earth vertical of the map frame**, whose origin
sat at the pier: at 10.7 km range the earth-curvature drop put the boat 6.7 m
below the datum plane. Relaunching on station to re-anchor the origin fixed the
whole chain. And **CAMP segfaulted five times**, on what the fault addresses show
to be one reproducible code path.

This deployment is closed on the field record. The code it produced is **not**
finished — two feature branches were written and reviewed on the water and
neither has been compiled-and-tested end to end. They are tracked separately, not
buried here.

## Lessons Learned

- **A parameter that reads back correctly proves nothing about whether it was
  applied**, and this cost real time and a real outage. `udp_bridge`'s
  `on_set_parameters` callback handles only two resend-threshold parameters;
  every other parameter is accepted and stored by ROS but read only at configure
  time. A runtime set on any connection setting is therefore silently inert while
  reading back as the value you set. The correct check is behavioural —
  `effective_rate_limit` against the floor — never the readback. The same trap
  was then found reproduced in the new cube code during review.

- **Rank by measured bytes before reasoning from a prior.** Hours went into
  shedding camera video as a bandwidth problem. Ranking the topics showed the
  cameras were under 4 % of offered load while a single nav visualisation topic
  (`received_global_plan`) dominated. The field agent recorded this against
  itself.

- **Read the right column.** `message_bytes_per_second` in `TopicStatistics` is
  the rate on the *source* topic as published locally; what actually reaches the
  link is the separate `send` `DataRates` block. Conflating them overstated one
  topic's link cost by ~10×.

- **A lifecycle re-configure is not a cheap way to apply config.** Predicted "a
  few seconds", cost ~3 minutes with the operator link fully down — configure did
  not return within 25 s and left the node unconfigured — **and the change did
  not apply anyway**, because configure re-reads the YAML and reset the staged
  value.

- **Stop at the first closed door and you will miss the answer.** The CAMP crash
  investigation reported the kernel log unreadable because `dmesg` was blocked by
  `kernel.dmesg_restrict`. The user is in `adm`; `/var/log/kern.log`,
  `/var/log/syslog` and the journal were readable the whole time and held the
  segfault records.

- **Subtracting the ASLR base turns three crashes into one bug.** All three libc
  faults resolved to `libc+0x85e55` — identical, so one machine instruction, not
  three coincidences. Worth doing before theorising about mechanism.

- **Isolate the build when the tree is live.** The cube branch was compiled into
  a scratchpad workspace with explicit `--base-paths/--build-base/--install-base`
  so `sensors_ws/install` — the tree the boat was running from — was never
  written to. Building into `sensors_ws` would have made the new binary live the
  instant the build finished, picked up by any respawn including a crash-respawn,
  on a node running `respawn=True`.

- **Runtime bridge changes do not survive a relaunch, and the relaunch was
  planned.** Every `remove_advertise` made during the transit reverted at the
  09:58 re-anchor. The agent enumerated exactly what would come back before the
  operator pulled the trigger, which is the right order.
