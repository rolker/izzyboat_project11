## Operator corrections to field-agent conclusions

1. **Drift #1 (~11:52) is NOT the "done cursor" and NOT "RTK lost"** — both field
   misreads. Bag reconstruction: GUIDED throughout (no mode flip) and **RTK_FIXED
   throughout** (the "status 0" was `NavSatFix` SBAS/GBAS, not an RTK indicator).
   Real cause = the **survey line-to-line transition lead-in**: a leg completed,
   the lead-in transit to the next line **overshot its goal (`RemovePassedGoals`
   2.5 m) and zero-cmd'd before handing off**, and nothing station-kept the gap →
   drift (~3.5 min until operator parked in `Hover` + re-engaged). Recurrence of
   #28. Filed **unh_marine_navigation#77**.
2. **CA-off is a valid operating mode WITH heightened operator vigilance** — not a
   prohibition/gate (operator risk-acceptance). Clean run today, **but in the
   closed-to-boaters section.** The CA-FP fix (`ca_safety` min-points/cluster
   threshold + upstream segmentation FP reduction) is a **reliability /
   operator-load improvement** (lets CA stay reliably on as an automated
   backstop), scaling with traffic — not a hard prerequisite.
3. **Battery: no FCU voltage failsafe is INTENTIONAL**, not a gap — managed
   manually via the boat's **voltage annunciators**. An FCU failsafe would
   auto-act (RTL/hold/disarm), unwanted under operator oversight mid-survey.
   (Reconsider only for unsupervised/OTH ops.)
4. **SVS data quality: the affected window is ~1 h, not ~2 h.** Survey-with-frozen-
   SV ≈ 13:52→~14:55 (then dock stop / stack down). M3 held ~1493.3 vs true
   ~1492.3 → **~+1 m/s ≈ 0.07%**, negligible in shallow freshwater; the `.all`
   records the applied SV so the window is trivially re-correctable.
5. **The day's "network issues" = zenoh/CAMP discovery instability**, not the
   udp_bridge queue tweak (the agent initially mis-attributed to OmniTIK/CAKE/OAK,
   then corrected; queue config verified intact + fail-freshing).
