## Summary

**First autonomous path planned around camera-detected obstacles** — the headline. After the nav2 config-split + 240-footprint cutover ([seafloor#3](https://github.com/rolker/seafloor_echoboat_project11/issues/3) / PR #29 + [PR #185](https://github.com/rolker/unh_echoboats_project11/pull/185)) landed on the boat, BizzyBoat planned a route threading between a sailboat and a buoy it detected with its own cameras (~13:56 EDT) — the segmentation → costmap → planner loop closing on real, non-charted obstacles on-water for the first time. Run in deliberately wet/overcast conditions. All three must-verifies passed (rig + reflex intact, nav2 clean, 240 footprint planning normal). The flip side: small/dim mooring buoys marked poorly under dark skies, and the planner got stuck in dense-buoy geometries (the collision-avoidance behaved correctly — the gap is planning maturity).

**Fixed in-deployment:** two silent stale-build failures on gabby (`sea_surface_segmentation` missing `SeaSurfaceRelayLayer`; `marine_nav` BT missing `SetTaskFailed`) — `make sync` pulls source but doesn't rebuild; caught and rebuilt, nav2 came up clean.

**Findings (data-confirmed at wrap-up):** the hover-latch is a **CAMP-side command-send gap** (the re-issued hover commands were never published — not a nav bug); small-buoy marking is limited by the strict argmax gate scoring marginal-red as water + dark-sky segmentation false-negatives; the diagnostics + BT-log combs are clean (fail-forward and planner verified healthy).

**Follow-ups filed:** segmentation marking gate + graded vote ([unh_marine_perception#22](https://github.com/rolker/unh_marine_perception/issues/22)), algorithm-core export enabler ([unh_marine_perception#23](https://github.com/rolker/unh_marine_perception/issues/23)), offline tuning tool ([marine_perception_tools#1](https://github.com/rolker/marine_perception_tools/issues/1)) + ui_ws manifest ([unh_marine_autonomy#130](https://github.com/rolker/unh_marine_autonomy/issues/130)); charger idle-current capture + power-model review (#196); CA-overlay #183 strengthened; timestamp-fabrication incident ([ros2_agent_workspace#504](https://github.com/rolker/ros2_agent_workspace/issues/504)).

## Lessons Learned

**The perception → planning loop works; robustness is the open question.** Today proved the loop closes on real obstacles (the milestone). The remaining problem isn't capability, it's reliability — small / dim / low-contrast targets under poor light still drop out. That's exactly what the offline tuning tool ([marine_perception_tools#1](https://github.com/rolker/marine_perception_tools/issues/1)) is for: tune the real marking algorithm against recorded bags instead of live `ros2 param set` pulses on the water.

**Better planning — not CA tuning — is the next priority.** The collision-avoidance behaved correctly; the boat got stuck because the planner drove into dense-buoy geometries it couldn't gracefully escape (it then failed-forward and moved on, by design). Sharpens the standing "obstacle avoidance is next" theme: CA works, planning quality in clutter is the gap.

**Trust the data over reports and hypotheses.** Operator launch/recovery reports lag the physical events by minutes (the crane ritual) — the altitude + motion data is authoritative. And the command bag killed two plausible nav-stack stories for the hover-latch; the commands were simply never sent. Reach for the operator-side command bag early when "the boat ignored me."

**Sync-without-rebuild bit twice** — both nav2 bring-up failures were stale `.so`s after `make sync`, silent at the launch console (errors only in node logs). A staleness / build check belongs in deployment bring-up.

**Segmentation → costmap — operator ideas (seed for a forward design issue, not #186 wrap-up).**

*(A) Marking-algorithm change.* → Opened as [rolker/unh_marine_perception#22](https://github.com/rolker/unh_marine_perception/issues/22). The segmentation node encodes output as **per-class probability mapped onto the RGB channels** (one class → one channel), and there are exactly **3 classes ↔ 3 channels** (operator notes this fit looks almost intentional). Operator's hypothesis: the current costmap layer may simply threshold the **red** channel (`red > threshold` → obstacle). Proposed improvement — mark an obstacle when **red is the argmax class** (`R > G AND R > B`) rather than an absolute red threshold; or, better, map **how much R exceeds the other channels** to a graded **cost value** (proportional marking) instead of a binary lethal/free decision. This would make marking robust to overall brightness shifts (e.g. dark skies lowering all channels) since it keys on the *relative* class confidence, not an absolute level.

*Verified against source (wrap-up, 2026-05-28):* the classifier is **already argmax-on-red** — `is_obstacle_pixel` = `R > G && R > B` (`segments_projection.hpp:44`), shared by **both** the costmap layer (`sea_surface_layer.cpp` includes it) and the CA reflex pointcloud (`segments_to_pointcloud.cpp`). So variant-1 is already in place; there is no red *threshold*. The un-built part is **variant-2**: the per-pixel vote into the log-odds buffer (`occupancy_buffer.hpp`) is **binary** — an obstacle pixel adds a flat `hit_log_odds` (0.85), water adds `miss_log_odds`, cell goes lethal at `lethal_threshold`. The red-dominance *margin* is not used for the costmap vote, though `ProjectedPoint` already preserves the red-channel intensity downstream (unused by the occupancy buffer). Variant-2 = scale the `hit()` increment by the red-dominance margin — contained change, plumbing half-present. **Nuance:** argmax is already brightness-invariant, so this helps **marginal/near-tie** pixels (partial evidence instead of a hard hit/cull cliff), NOT pixels the model fully misclassifies under dark skies (those R-not-winning pixels need model/exposure work — the §21 thread).

*(A′) Operator observation that sharpens (A) — "red visible in segmentation, but no costmap mark."* Operator saw a **red mark at a buoy in the segmentation image — dimmer than other targets — that did not register on the costmap**. Since the model *did* emit a red signal, the failure is downstream of the model, not (only) a model miss. Verified mechanism from source: the costmap gate (`project_observations_inverse` in `segments_projection.hpp`, used by `sea_surface_layer.cpp`) classifies each cell by `is_obstacle_pixel` = strict `R > G && R > B`. A cell that **fails** it is pushed as a **miss** ("positively observed water"), i.e. it actively adds `miss_log_odds` *against* the cell — not neutral. So a dim-red buoy pixel where R is present but **not strictly the max** (looks reddish to the eye, but G or B ties/exceeds numerically) is scored as water and **clears** the cell. Most-consistent reading; **confirmable from the recorded frame** (read the actual RGB values where the operator saw red-no-mark). Implication for (A): the real lever is likely the **gate** (widen "obstacle" to marginal-red — e.g. R within a margin of the max, or R above a fraction of the sum), not only grading the hit increment; pure variant-2 doesn't help a pixel that fails the strict argmax. This is exactly what tool (B) would let us inspect frame-by-frame.
